# PLAN-798：P95 周转与热重载扩展策略澄清（2026-10-20）

用户最终确认保留 **P95 <1000ms**，不改为算术平均。开发体验的长期目标是在工程完成初始化并得到首个结果之后，持续处理不同位置和类型的代码修改，至当前修订的新结果或准确诊断可见。首次启动/初始工程装载单独计量；修改实际触发的依赖检查、编译、验证、安装、执行与呈现仍计入，不得每轮重新声明“初始化”来排除工作。

本轮仅澄清推进策略和架构责任，**没有修改798既定负载、两条正式P95硬门、预算、AC/V/任务或实际热重载非目标**。不新增常驻会话/完整热重载实施phase；plan_revision=5、executing8/11保持，历史review和失败原样保留。此前聊天提出“改均值”“798追加常驻会话phase”未落入执行合同，均不作为本轮决策。

## 两种办法如何使用

1. **实测主线**：先让当前已实现流程在其冻结代表负载和真实入口上达到P95<1s；每次接入语言、依赖、装载或热重载功能，都以同等正确性/安全检查重新测量其受影响路径，保留对照与原样本。新能力的支持矩阵/入口另由所属Plan冻结，不能仅复测旧标量程序宣称新能力亚秒。
2. **预估辅助**：对尚未实现的工作建立成本清单，说明输入规模、重算/分配/IO次数、估计区间、参考来源、串并行关系及未知项；用于判断余量与安排实现/优化次序。无依据的项标未知，不能捏造毫秒数，也不能以估计通过代替实际验收。
3. 独立阶段的P95不能直接相加充当整体P95；预测需说明假设和长尾/共享负载风险。已有跨进程初始化开销不能直接抵扣未来热安装/保活开销，反向也不能把当前整个请求时间解释成编译器/VM计算极限。
4. 接入新功能后如实记录超标，先按trace定位并评估优化；若确需改变目标，显式修订相关Plan并由用户决定。原目标不会因功能扩展自动提高，也不预先承诺任何复杂元程序/全冷构建都亚秒。

## 架构弹性在当前就承担，完整功能分期交付

沿用 Design43 §6.1–6.3 和 Design40，保留共同语义/IR/store；不另建一套热重载编译器、身份体系或缓存数据库。每个后续Plan在相关模块扩展时，必须说明下列适用接缝的实际状态与owner，而不把“以后支持热重载”当作实现证明。

| 接缝 | 现在的设计约束 | 后续实现/验收责任 |
|---|---|---|
| 逻辑单元与版本 | 声明/实例逻辑身份与body/interface/layout修订分开；局部槽、表下标或进程地址不是永久跨版本ABI | 语义/增量owner与最小热重载owner验证版本变化、失效和新旧调用选择 |
| 编译、装载与安装 | 产物构建、验证装载、候选安装及执行有明确边界；单次worker启动不是唯一永久会话接口 | 常驻开发会话/最小AV热重载Plan落实多次编辑与候选安装；不要求798本轮实现 |
| 依赖与CTE | 区分body、接口、布局、配置、Meta/CTE及负依赖；缓存结果绑定真实输入 | 各新增语言/CTE/profile owner完成实际失效与fresh对照；不假称现有前端已精细增量 |
| 修订与提交 | 请求绑定snapshot；候选完整验证后提交，失败保持可用旧版，迟到结果不能覆盖新修订 | 发布/重载owner验证安装提交点、失败和取消路径 |
| 活版本与资源 | 预留generation/lease/owner关系，旧调用/对象/闭包的清理代码不得提前回收，旧代总量有界 | runtime与数据profile owner按实际支持面实现保活/回收；状态迁移、活帧迁移、OSR另行冻结，不默认全支持 |
| 计量 | 初始化、热态编辑、重启恢复分列；记录真实重算、验证、装载、发布及峰值 | 当前798 owner维护现有trace/硬门；后续功能owner补新增阶段并复测同一修订端到端结果 |

这些是已有架构合同的适用说明，不表示798已具在线切换、活对象迁移或完整代际管理。798的有限准入/身份模型和受管cache须继续按其当前AC验收；后续Plan不得把明确的公共单元/加载接缝固化成不可替换的“一次启动、一次编译、一次退出”假设。发现这种冲突时，在该功能实施前给出有界调整，不等完整语言或UI完成后再统一改框架。
