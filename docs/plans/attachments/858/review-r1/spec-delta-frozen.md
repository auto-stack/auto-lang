## M2 sample research and boundaries

Two original one-level samples are defined by `docs/design/autographics/m2-game-sample-matrix.md`: G2-01..09 cover a 2D side-scrolling platform level with movement, one grounded jump, walls/ceiling/platforms, pits, three collectibles, one patrol enemy, failure/win/restart, bounded following camera, sprites/sound/HUD; G3-01..08 cover a 3D third-person platform exploration level with camera-relative movement, one jump, static platforms/hazards, three collectibles and a goal, failure/win/restart, orbit/zoom camera, visuals/sound/HUD. The matrix supplies the inputs, coordinates, state transitions, negative controls and subsequent verification requirements. These are future acceptance requirements, not an implemented game or a complete recreation of a reference.

References as read 2026-10-27: Godot demo projects `b761b4cd5718a7118f2c95eb55f181d0a5f004f1` (`2d/platformer` primary 2D, `3d/platformer` comparison); Kenney Starter Kit 3D Platformer `3fa8a04b1c01ab23db43123d4ce814a34c3fc7f0` (3D primary). Original 2D player invincibility, slopes, bullets, moving platforms and double jump and Kenney double jump/falling platforms are not silently adopted as the M2 rules.

Selected raw source assets and full per-file SHA-256/length/dependencies/notices are indexed in `docs/plans/attachments/858/selected-source-candidate.json`; original files are retrieved at the pinned source commit. Kenney's README declares included models, sprites and audio CC0; Lilita font carries OFL 1.1 and reserved-name notice separately. Godot 2D candidate artwork/audio with unresolved individual provenance is excluded. Character frames and game-specific artifacts are future derivations and have no produced bytes or hashes yet. Input sums are 149188 bytes for 2D, 198763 for 3D and 203825 deduplicated, including notices; these are source-input totals, not measured packages. Model images are external and character animation exists; current static GLB admission excludes textures/URIs/animation, so original models do not prove support.

The delivered baseline is 854 graphics `523d27b863dbe306c89af0ea546334225a29f8e9`, SDK `7b987ca8b12f2eec3c076a1bfbf3ff4663aa8467`; 855 delivery `05fdc81c546aff735eefdb6c39fbc5fb35dc546a` did not change the behavior API files. Behavior/1 offers bounded existing graph traversal, translation/visibility and limited input, behavior/2 finite AABB queries and behavior/5 bounded two-contact move-and-slide. These do not establish a complete character controller, object lifecycle, trigger service, public runtime camera, sprite/animation, public audio/HUD or portable full game SDK. Existing Squash audio/HUD/camera are specialized. Per-G classifications, limits, failure cases and planned probes are in the matrix.

Follow-on work first measures actual Auto CPU/resources and role/character feasibility, then establishes public input/character and object lifecycle, triggers/state, runtime camera and presentation, and finally independent game loops/audio/HUD. Work can be split according to actual dependencies; no ACE or preassigned plan IDs are implied. Each independent game must ultimately pin engine/SDK/assets, specify origin, license, length and hash with safe relative paths, and provide a complete relocatable offline closure with corruption/missing-file refusal and recovery. A source-input inventory is not a published package, downloader, working conversion, offline test, performance pass or authorization to release.
