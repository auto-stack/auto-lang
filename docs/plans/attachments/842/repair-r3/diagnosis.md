# PLAN-842 连续独立复审不通过：共同不变量诊断

R2、R3 是连续两次独立 final needs_fix（之前同会话 R1 非独立）；原始结论分别见 [R2](../review-r2/report.md)、[R3](../review-r3/report.md)。本检查点按 auto-plan-work 连续两次失败要求先诊断，不降低验收或重新请求授权。

## 剩余不变量

1. 受管 Full 安装被自动选中或由明确源覆盖选中时，其有效清单和整个实际 SDK 消费闭包才是权威；manifest、包身份、缺失/额外文件和每个被消费文件的收据 bytes/hash 必须一致。SDK 缺失或坏数据不能回落，也不能改写旧工作区/交付。合法未受管开发源及合法显式 UI 覆盖仍受原合同支持。
2. 一次成功的预检不是复制完成的证明。正式交付每个语言/UI crate、patch 和根输入必须以冻结的安装收据核对 staging 中实际原始字节；投影改写在核对之后。由根清单/锁派生的工作区和 pin 必须消费已与同一收据核对的实际读取字节，收据在事务结束前不可漂移；任何失败均发生在旧交付换装前。哈希只用于一致性，不声称签名或恶意攻击防护。
3. R2 把工作区明确引用的四个 crate 当成整个运行时闭包，遗漏了 Cargo 传递依赖、复制的其他 crate、根资源、根锁和 patch；并把复制前校验当成后续复制不变。原测试仅破坏 auto-lang manifest 或缺整个 auto-lang，未针对其他输入的内容/额外/缺失及预检后漂移设置区分性 oracle。

## 调整与 oracle

- 将受管 SDK 收据解析及文件集合校验设为单一共享入口；枚举全部受管 SDK 文件、核对完整集合和内容，明确排除工作缓存目录；不通过一份固定四包名单声称完整闭包。核对有效清单、所有权/输入及源版本，合规开发源不被当安装。
- 交付对各实际 copied crate、patch 和根输入，在投影前用同一次冻结收据校验 staging 副本，读取根 manifest/锁时核对被消费字节，避免只复查源或事后凭成功返回推定 copy 正确；提交前检查收据身份未改变。
- 针对实际 Full 安装及旧产物，分别覆盖语言传递依赖、增加/缺失文件、根输入、根锁、patch，保留相同字节哨兵和 manifest；预检后改变来源的可控真实 staging 反例必须证明失败且旧产物不变。恢复后重验和有效显式/UI 开发源正控；工作区入口也须覆盖传递依赖。使用动态实际闭包及类别边界控制，而非只重跑旧四包例子。
- 重新绑定最终源码、Core/Full 安装与外部消费；21 项测试迁移及 guard 证据仅在代码、清单和选择配置不变时复用。完成后再独立复审；整档仍为 review pass 后的 merge 所有。

## 显式覆盖邻接控制

R3 修复过程中以实际安装额外复现：移走安装 receipt，同时设置 `AUTO_LANG_ROOT` 指向该可执行文件邻接 SDK，并显式提供合法 UI 开发源，旧实现仍 exit 0 且覆盖旧 app。即使来源以显式参数给出，也不能将当前可执行文件邻接 SDK 降级解释成无收据的普通开发源；需对 `AUTO_LANG_ROOT`、`AUTO_LANG_CRATE` 和交付显式根均测试拒绝和旧字节保全。普通非安装开发目录仍合法。

以另一份具 Full 安装双执行文件、但缺清单的显式 SDK 实际重放，同样发生 exit 0 与旧 app 覆盖。调整识别同时覆盖所运行程序的邻接 SDK、具有安装收据的 SDK 和具有 Full 安装双执行文件的 SDK；仅有普通独立 SDK 源目录仍保留开发模式。

## 非受管开发源传递依赖控制

真实 `AUTO_LANG_ROOT` 指向一个含真实 workspace 与四个直接包清单/入口、但缺 `auto-val` 等实际路径依赖的独立目录时，旧版仍 exit 0 并覆盖旧 app。受管清单校验不适用于自由开发源，需对选中 Cargo 包的本地路径依赖闭包（包含 workspace 继承与目标依赖）执行结构预检，保留正常未提交开发源码与无网络注册表依赖，不再以四个目录存在冒充完整。合法现有开发组、安装 SDK 与显式 UI 源必须实际正控。

UI 显式开发源同样可能在 package 和 lib 存在时缺实际路径依赖；工作区和交付选择应对语言与 UI 所选本地 Cargo 路径依赖使用同一结构检查。回归覆盖目标条件依赖、workspace 继承与环；真实完整三仓开发源为正控。
