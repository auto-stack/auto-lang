# PLAN-842 R5/R6 连续 final 非通过：多来源冻结收据诊断（修复前）

> 后续修复与重新验证见 [修复报告](report.md)；仍待独立最终复审。

R5 的 SDK 路径身份和无效本地版本已做统一修复并重验证；最新独立 R6 又发现**显式受管 UI 来源**复制期与来源身份漏判。两次连续独立 final 未通过，按 auto-plan-work 必须先记录共同不变量、漏测原因和差异化 oracle，再修复；本诊断不是通过结论。

## 不变量与已证反例

- 真实交付可同时选语言 producer 与独立 UI owner。无论 UI 来源是默认受管安装、显式指向同一安装、显式指向另一份受管 Full 安装，还是合法非受管开发源，必须冻结**实际被选中的每个受管来源**的收据；复制入 staging 的每个受管 UI crate 的所有权和实际字节须按该 UI 收据校验，提交前再次核验该收据未变。任何预检后短时篡改即便在 swap 前恢复，也不得进入交付或覆盖旧产物。
- 实际 `AUTO_UI_SOURCE_ROOT=同一安装/sdk` 下，独立子代理在 preflight 完成后的 staging 窗口篡改 UI compiler 文件，待复制后立即恢复，真实生成 exit 0、坏字节进入交付且旧 app sentinel 被覆盖；根因是 `rust_ui.rs` 只在未设置 `AUTO_UI_SOURCE_ROOT` 时对 UI staging 调用安装收据校验，错误地把“显式 UI 源”当作“非受管 UI 源”。先前 R3/工作期漂移仅注入默认语言 crate，虽覆盖源恢复但未覆盖显式受管 UI 图。
- 当语言安装 A 显式选另一份已 verify 的受管 UI 安装 B 时，实际交付 `ui_source_root=B/sdk`，`ui_git_head=null`，而 B 的清单有 UI 来源 SHA；根因是 identity 只从语言 producer 的收据派生，未冻结/记录 UI B 的实际收据。R5 正控只验证同一安装 alias，漏独立受管 UI owner 的身份。

## 修复与差异化验证

1. 在生产入口识别所选 UI 根，独立捕获其安装收据和来源 SHA；受管无/坏收据具名拒绝。默认同源可共用来源语义，不能因显式选择而跳过受管检查；另一份安装必须以其自身收据而非语言收据为准。非受管 UI 不强制收据，并以其自身 Git 身份或未知值记录，不借用安装 A 的 SHA。
2. 对每个被复制 UI crate 的 staging 原始字节应用对应冻结 UI 收据的 owner/path/hash 集合，投影前验证；结束 swap 前复核所有实际受管收据。原语言 producer、根锁/patch 的验证及显式优先级保持。
3. 区分性真实 CLI 对照：默认、显式同安装、显式不同安装三个 UI 来源各做真实 staging 期间修改后恢复；观察复制点和源恢复，均必须具名拒绝并逐字保留原交付，恢复后重新生成成功。不同安装身份 SHA 必须来自 B 收据；普通开发 UI 合法正控与坏开发源继续通过预期控制。保留根语言与复制期旧反例、版本/Windows SDK alias 正反控及完整安装消费证据，最终 rebind。
