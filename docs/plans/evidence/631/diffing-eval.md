# PLAN-631 T-06：VM 动态视图结构 diffing / 细粒度失效评估（bounded）

结论先行：**不建议在本计划内冒进立项**；以"门槛触发式"复查替代
（详见 §3），届时的首选方案是 §2.3 的行级 memo 而非通用结构 diffing。

## 1. 现状量化（T-01/T-03 剖析数据，见 profile.md）

- T-03 落地后 debug 列表选中整重建：p90 9.8ms / max 16.5ms（67 行）；
  opt p90 ~2.6ms。60fps 帧预算 16.6ms 下 debug 已入区间（max 贴线）。
- 残余成本结构：builder（AbstractView 重建，含缓存命中克隆）~9.8ms +
  render（AbstractView → iced Element 全量构造：widget 分配/样式闭包/
  lucide 查表）~5ms。两者都是"每元素全量重做"。

## 2. 方案评估

### 2.1 结构级 diffing（VM 视图树 → 树编辑序列）
- 收益上限：debug 整重建 ~10-15ms → 理论 <2ms（仅变更子树重转换）。
- 成本：DynamicComponent/ForLoop 槽位与 bindings 语义需可哈希化的
  表达式依赖面；aura_view_builder 转换器 17k 行，diff 正确性面广
  （列表增删/排序/键控、popover/portal 挂载点、事件闭包身份）。
  iced 侧还要 Element 身份稳定化（现每帧新 Element，iced 内部 diff
  已吃掉大部分 widget 状态保留）。
- 风险：正确性回归面 = 全部动态 UI；与现有 slot/试探（probe）、
  untracked 臂、缓存帧账本（PLAN-062）强耦合。
- 判断：工程量 ≥ 一个 L2 程序（设计文档 + 多 plan 分解），当前量化
  收益（debug 10ms 级、opt <2ms 级）不支撑。

### 2.2 依赖追踪细粒度失效（state 写 → 受影响子树标脏）
- 收益同上；成本：状态读路径需侵入 aura 表达式求值器（.at 解释层），
  VM 轨每状态读登记依赖图——运行时常开销换重建省时，与 T-03 缓存的
  "读时零记账"取向相悖。
- 判断：不做。

### 2.3 行级 memo（列表项子树转换缓存，键 = item 派生串）
- 收益：67 行列表选中帧的 builder 段大头是 ForLoop 全行重转换；行
  memo（键 = item 数据指纹 + 类串版本）可把 67 行 → 1 行重转换，
  builder ~9.8ms → ~2ms 级（debug）。范围小：ForLoop 臂局部，不触
  表达式求值器语义。
- 风险：键遗漏（行内绑定状态）→ 陈旧 UI；需 probe/slot 兼容性核对。
- 判断：**若未来需要**，这是第一候选（成本/收益比最优），且可与
  T-03 缓存正交叠加。

## 3. 复查门槛（触发任一即重启评估）

1. 消费方列表规模 ×4（~270 行）或单帧行内组件密度显著上升，debug
   整重建 max 越过 16.6ms（掉帧线）。
2. 低端宿主（非本机）实测选中 > 50ms。
3. 出现"全量重转换导致可感知卡顿"的新消费场景（如拖拽实时预览）。

触发后按 §2.3 → §2.1 顺序立项。

## 4. 对计划 §10 Q2 的回答

"结构 diffing 是否立项"：**现在不立**（数据支持）；保留 §2.3 行级
memo 为后续候选，由消费方规模增长触发（§3 门槛）。
