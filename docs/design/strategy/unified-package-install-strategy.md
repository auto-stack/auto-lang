# AutoMan：统一 Package / Install 体系（设计讨论草案）

> 日期：2026-10-03。输入：本次用户讨论及当前本地快照。
> 用户确认：这是 v0.6 必做方向，扩展到 AutoOS 的应用、代码工程、知识库、用户数据等实体，
> 统一由 auto-man 管理；Launcher 与 shell 提供搜索、安装、更新、卸载。
> 本文：目标架构与验收建议，尚未实施或批准具体技术方案。
> 版本规划：[v0.6 roadmap](../../roadmap-v0.6.md)。正式执行仍需架构评审与分解 Plan；
> 主电脑尚不可访问，暂不依据旧 `.next-id` 分配正式设计/Plan 编号。

## 1. 目标与现状

目标是把语言开发和系统使用纳入同一包网络：统一身份、来源、版本、依赖解析、
下载/制品存储、安装状态与生命周期。体现用户提出的 LaOS 理念。
“终极包管理”是持续演进的产品目标，v0.6 需交付真实可用的统一核心与代表性实体闭环。

当前快照可复用的输入：

- `crates/auto-man/src/pac.rs`：pac 工程描述、targets 与 workspace。
- `resolver.rs` / `git.rs` / `index.rs`：源码依赖解析、获取与索引。
- `lock.rs`：现有 `pac.lock` 锁定 Git 版本/commit/路径；系统级制品锁定需扩展设计。
- `builder*`：已有多工具链构建编排。
- `cache.rs`：源码文件状态的构建缓存；不能直接当作系统安装数据库。
- 现有调用 bun/npm/pnpm 安装前端依赖与配置安装，不代表已经具备 AutoOS 全实体安装体系。

完整 v0.5 恢复后需重核以上现状，以及 auto-cache 等已有存储能力可复用的范围。

## 2. 统一核心与实体语义

| 层 | 建议职责 |
|---|---|
| Package Identity / Manifest | 名称空间、版本、来源、提供的能力与实体描述；沿用/扩展 pac.at，核对与 AppManifest 的关系 |
| Dependency Resolver / Lock | 精确解析身份/版本/制品，区分依赖种类和 scope，记录可复现结果 |
| Fetch / Artifact Store | 下载、校验、离线缓存、不可变内容寻址存储；记录制品目标与工具链兼容性 |
| Build / Adapter | 需要构建时调用对应工具链；将宿主生态管理能力接入统一编排 |
| Profile / Install State | 区分项目依赖、用户安装列表与系统配置；记录当前选用版本和保留代际 |
| Install Lifecycle | 规划、获取、校验、准备、激活、更新、撤销与清理；明确失败恢复边界 |
| Entity Adapters | 应用入口、代码工程、知识包及用户数据各自的激活、迁移与卸载行为 |
| Shared Service API | CLI、Launcher 与未来应用市场共享同一操作与任务状态模型 |

统一依赖网络需要带类型的边，例如 build/runtime/content/schema 依赖。
知识的语义关联、数据归属/权限、资源引用另行表达；不能把所有关联都当作
会触发安装或版本求解的依赖。循环与多版本规则须按边类型定义。

实体可以混合提供多种能力，一个 package 不必强制只能属于一个互斥类别。

### 2.1 应用

应用包描述身份、入口、兼容域、运行时依赖与可用制品。
VM/ABC、a2r/native 可执行文件等是同一逻辑应用的执行表示，需与 AutoScape Provider 契约对齐。
安装后的应用由 Launcher/Resolver 发现，不要求重新编译桌面宿主。

### 2.2 代码工程

保留本地源码编辑、workspace、path/Git 开发依赖与现有锁文件迁移路径。
已安装不可变包与可编辑工程分别管理；开发覆盖规则必须明确。
构建制品按源码、依赖、target、工具链/ABI、features、flags 等完整输入标识，
避免只按包名/版本共享不兼容产物。

### 2.3 知识包

管理知识包版本、依赖、来源、schema 与导出资源；支持项目/个人 scope 引用共享知识包。
包发布版本与用户的注释/整理结果分别保存，便于更新共享资料并保留本地补充。
v0.6 验收基本包安装/引用/更新能力，完整知识管理工作流仍在 v0.7 成为主线。

### 2.4 用户数据

用户数据进入统一身份与管理模型，同时保持可变、私有与用户所有的语义。
可研究 data package / workspace 的 schema、版本化快照、导入导出和迁移；
在线编辑数据不作为所有人共享的不可变发布包处理。
公共制品 store 与私有数据空间按权限隔离；共享去重边界需明确。
应用卸载默认保留用户数据，数据清理与数据迁移具有独立、明确的操作语义。
用户数据的所有权/引用不自动等于包解析依赖。

## 3. 存储、安装与更新建议

### 3.1 存储与依赖映射

源包、知识发布包与可执行制品可共享不可变内容寻址存储；
项目和用户 profile 记录解析结果与映射，不在每个 Auto 工程复制整个依赖目录树。
该 store 可以分来源、用户权限及制品兼容域，不要求所有实体共用无权限区分的一个目录。

Auto 的 resolver 可直接消费包/制品映射，物理目录不作为依赖关系的唯一载体。
外部生态 adapter 需保留其必要解析/构建语义，不能承诺第一版消灭所有外部 node_modules。
不照搬 pnpm 的 symlink 目录布局：本仓 worktree 禁止 junction/symlink。
共享不可变文件的复用方式需保证开发编辑不会修改 store；优先考虑路径映射、
独立副本或支持时的 copy-on-write，具体方式经平台验证后决定。

### 3.2 安装事务与版本状态

建议操作流程：解析并显示计划 → 获取/校验 → 构建或选择制品 → 准备新代际 →
提交激活状态 → 发布系统事件。CLI 与 Launcher 消费同一任务状态。
需验证断网、中断、重复请求、并发安装、损坏包和重启后的状态一致性。

更新应保留可恢复的旧包/安装状态，支持包代际切换与回滚。
运行中进程的制品保持规则必须明确；用户数据的 schema 迁移/降级另外定义，
不能把回滚可执行文件等同于自动回滚所有用户数据。

垃圾回收按可达性和保留规则设计，roots 包括有效 lock/profile、运行制品、
固定版本、回滚代际与数据快照等；不能仅因一个 app 卸载就删除其他 app 的共享依赖。

### 3.3 来源与发布

先支持明确的本地/Git/静态索引或制品源，定义发布身份、校验和与信任信息，
再演进到开放应用市场。市场的排名、用户列表与 OpenBusiness 商业机制有独立职责，
不作为下载/安装核心可用的前置。

原生包发布与安装契约应公开，官方与社区都能使用。
安装来源、包能力声明与必要权限需要被操作计划和 UI 清楚表达。
具体签名、执行 hooks 与隔离策略在正式架构设计中核定。

## 4. 用户入口与 v0.6 验收建议

用户提出的 CLI 目标：

```text
auto search "xxx"
auto install "xxx"
auto update "xxx"
auto uninstall "xxx"
```

Launcher 提供同一软件搜索/安装/更新/卸载操作，显示计划、进度、失败与当前状态。
它调用 auto-man 服务 API；不在 Launcher 内复制一套 resolver/installer。

建议 v0.6 验收：

1. 四类实体共享 package 身份、manifest/依赖/lock 机制，分别验证实际生命周期。
2. 原有源码工程路径兼容，至少一个项目可重复解析、获取与构建。
3. 官方独立 app 发布为可安装制品，Launcher 可发现并启动；四个主打 app 与
   28 个 demo 按发行矩阵消费安装路径，而非各自定制安装脚本。
4. CLI 与 Launcher 安装、升级、卸载使用相同核心；失败/中断恢复与共享依赖测试通过。
5. 一个知识包在个人与项目 scope 被引用，更新后保留本地补充。
6. 用户数据实体能执行约定的管理/快照/导入导出流程，应用卸载不误删数据。
7. 内容复用与版本隔离有实际磁盘/下载/构建数据，定义性能目标后测量。
8. 单机/固定平台安装闭环先成立；跨平台分别用 native adapter 验证。

以上是可审阅的范围建议，具体接口、支持环境和量化门槛需正式设计/Plan 确认。

## 5. 借鉴工具时按职责拆分

- Cargo：研究 manifest、锁定依赖与开发 workspace 的复现方式。
- npm：研究分发与开发者使用体验；Auto 原生解析路径直接表达依赖。
- pnpm：研究内容复用与依赖可见性，不能直接继承本仓禁止的 symlink 布局。
- Bun：研究下载/缓存/安装的性能与工具链整合，不由其出现推断其他工具已经失效。
- apt：研究系统包来源、依赖、升级与卸载的运维语义。
- CMake：研究多工具链构建目标、构建/安装编排的 adapter。
- Flatpak：研究应用/运行时分层、制品分发与安装版本管理。

它们承担的职责不同，统一入口背后需要清楚的模块边界，
不能简单合并所有命令、目录和全局依赖模型。

## 6. 截止 12 月底的实施位置

建议优先固定 package 身份、制品与可变数据边界，再确定 auto-man 拆仓契约。
auto-man 核心可以复用当前工具链独立实施，不等待 AAC 自举或 AutoScape 产品化。
新 CLI 先跑通，再由 Launcher 消费同一核心；应用独立化与知识原型尽早成为消费方。

这是新增关键路径，需要重新核算主线资源与月度里程碑。
建议将“外部安装格式全部兼容/接管”、复杂分布式 registry、跨设备数据同步与迁移、
完整应用市场、全量高阶构建优化列为 v0.7+ 候选；AutoOS 原生统一安装闭环仍属 v0.6 必做。
具体延期不自动变更既有已批准计划，应在审阅范围后确定。
