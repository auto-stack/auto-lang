## 1. 版本定位与十条方向

AutoOS 的长期目标是借助 AI 与 Auto 生态能力，构建以人为本、服务用户的个人操作系统。
新交互形式与应用演进共同支撑个人服务；知识仓库服务是第一条贯穿系统框架的路线。
v0.6 围绕工程体系整理、原生编译自举、平台化、应用产品演进及知识管理原型探索展开。
v0.5 的语言/Rust 生态、Web/iced UI、虚拟桌面和应用能力是待发布基线，
不得因提前开展 v0.6 而混入未验收重构。

| 方向 | 已确认目标 | 实施时需明确的边界 |
|---|---|---|
| 1. 工程整理与编译器架构 | auto-lang / auto-ui / auto-man 拆开，后两者独立到外部仓库；整理架构、工程组织、文档与知识；覆盖 Rust 代码复审、重构及 Auto 对应实现；AC/AAC 自主编译器架构为主打产品 | 明确 HIR、首个 native target、运行时/互操作与真实自举验收；旧后端全迁移及全仓深层重构为延期候选，见 §1.5 |
| 2. AutoUI / AutoOS 平台化 | Linux 生态全支持为主打交付；鸿蒙至少做到虚拟桌面与 28 个 demo 正常运行，复杂独立 app 可延后；Web/Windows 既有能力继续维护 | Linux 的发行版、硬件、桌面会话与系统集成矩阵待核定；鸿蒙需从 a2ark demo 基础验证整套桌面/28-app 场景 |
| 3. Python / AI / 科学计算 | Python 生态高级支持为主打交付，加强 PyTorch 等模型与库支持，使 Auto 可承担真实科学开发工作流 | 代表性任务、数据交换、GPU/设备、回调、错误诊断和可复现环境 |
| 4. ROS2 / Godot | ROS2 生态完整支持为主打交付；Godot 在 v0.6 以调研为主 | ROS2 发布/运行路径、接口与工具兼容范围、仿真/实机任务矩阵待核定；Godot 正式产品化为 v0.7 候选 |
| 5. AutoScape / AutoWeb | v0.6 以调研与原型为主，研究应用访问体系 | 既有 M1 + M2-lite 施工图作为输入，不再自动视为 v0.6 产品化承诺；正式交付为 v0.7 候选 |
| 6. 知识库与个人知识管理 OS | v0.6 做原型设计与调研性开发，验证统一 Jade 个人知识与 Musk 项目知识底座的方向；完整流程在 v0.7 成为主线 | v0.6 核定原型与调研范围；v0.7 推进完整跨应用知识管理流程 |
| 7. 主打 app 演进与应用独立化 | 持续开发 auto-shell、auto-musk、auto-edit、jade-edit；将 AutoOS 的 28 个 demo 产品版独立到单独仓库，与新的系统交互共同演进 | 核对完整 v0.5 的应用清单与状态；确定四个 app 的功能验收、教学版/产品版关系、跨应用流程及独立构建/发行 |
| 8. 系统级 Package / Install | v0.6 必做：由 auto-man 统一管理应用、代码工程、知识库、用户数据等实体的包网络；CLI 与 Launcher 搜索、安装、升级、卸载 | 固定包身份/依赖/制品、安装状态、可变数据生命周期、存储复用、失败恢复及平台验收；见 §1.6 |
| 9. 应用通信 / AutoAI | 用户追加为 v0.6 重点：以 Auto 为调用入口，连接应用、系统服务与 AI Agent，减少逐应用 MCP/CLI 胶水 | actor执行、typed调用/事件/流、Schema/编码与IPC分层；AutoAI能力描述、任务/取消/收据及MCP桥；技术建议见 §1.7 |
| 10. 系统级 DevTools | 用户追加为 v0.6 重点：应用按能力导出协议，OS提供Inspector与Agent接口，覆盖跨app/backend观察、操作、比较和诊断 | VM/Rust共同子集、第三方样板、树/布局/像素diff分别验收；不假设所有app拥有完整VTree/debug能力，见 §1.7 |

Android、macOS（Jetpack 路线）与 MCU/LVGL 等平台按本次讨论留给 v0.7 考虑。
十条方向的具体成熟度与发布验收清单尚待定；两项新增基础设施共用一条实施主线，需重新核定容量。

Linux 优先面向原生发行版与桌面会话；用户提出参考 Pop!_OS，并借助 COSMIC Desktop
架构推进。具体复用、集成或适配范围在 Linux 专项设计中核定，不将参考方向写成已有实现。

### 1.1 知识管理的版本分期（2026-10-03 用户确认）

**v0.6：原型设计与调研性开发。** 围绕完整流程研究数据模型、接口与用户体验，
通过小范围可运行原型验证关键假设。候选探针包括 AutoLens 采集与上下文快照、
AutoDown 知识整理、Jade/Musk scope 共享、来源追溯、检索，以及作品驱动学习。
这些是原型候选，不在本文预先要求全部实现；具体范围仍需设计与 Plan 确认。

建议沉淀架构与接口草案、可重复演示的原型、实验结果和未解决问题，
据此制定 v0.7 实施计划。完整知识管理流程的产品化不是 v0.6 发布门禁。

**v0.7：完整知识管理流程成为主线。** 以 v0.6 的验证结果为依据，推进
“遇见/采集 → 理解/整理 → 知识存储与关联 → 检索 → 学习与实践 → 创作 → 反馈沉淀”
的跨应用流程，连接 AutoLens、知识底座、Jade、Musk 与学习/创作能力。
具体交付范围与成熟度届时确定，不把原型实现直接当作已稳定的产品契约。

v0.6 的工程文档整理、规范归属与必要共享接口仍随工程重构推进；
它们与完整个人知识管理产品的分期分别验收。

### 1.2 个人操作系统与个人服务（2026-10-03 用户确认）

个人服务从人的目标与活动出发，贯穿系统交互、应用、AI 和资源管理。
应用提供具体能力，AutoOS 负责连接这些能力，使用户的活动可以跨应用连续进行。
新交互形式的具体设计仍待定，不能只以新增组件或窗口数量代替用户流程验收。

- **知识仓库服务**：首条个人服务路线，连接采集、整理、学习、实践与创作；
  沿用 v0.6 原型/v0.7 主线的分期。
- **Career 服务**：未来方向，辅助职业生涯、能力发展、作品与事业规划。
  用户提出以 AI、机器人、下一代互联网支持 OPC/小公司发展的形势作为设计假设，
  不将该市场判断写成已经发生的事实；此服务的版本归属和范围尚未确定。
- **娱乐等其他个人服务**：保留未来探索位置，具体用户需求与范围另行研究。

建议以代表性个人活动设计跨应用流程，验证用户是否能更好地完成目标、保留上下文、
管理自己的资料与成果，并理解和控制 AI 的参与。以上验收方法是建议，待设计细化。

### 1.3 OpenBusiness：共建内容与成本分摊

**价值原则（用户确认）**：AutoOS 与个人服务以服务用户为核心目标，
商业模式应支持服务的持续运行与内容共建。

**OpenBusiness 原则（用户确认）**：成本共担、用户主导、价格公开、分配透明。
AutoOS 推荐应用与服务围绕这些原则探索免费和收费模式；具体定价与分配机制仍待验证。

用户提出的远期探索路线：用户支付服务成本，社区共建内容并分摊成本，
探索通过交互式分摊形成市场价格，再以内容创作、分享及 AI 辅助内容提供增值服务。
这是待验证的商业/社区设计方向，不作为 v0.6 的平台上线承诺。

后续需研究成本口径、分摊对象与规则、交互式价格形成机制、创作者回报和社区治理。
实际机制、运营条件与可持续性应通过独立调研/实验验证，不能将概念当作已经成立的定价模型。
公共内容社区、Career 与娱乐服务的正式交付版本均待定。

### 1.4 开放应用生态与应用市场（2026-10-03 用户确认）

AutoOS 是开放的 OS，未来应用市场以分享、发现与竞争为核心。
开发者可以开发、上传并宣传应用，同类应用可以并存，面向不同用户形成各自的特色。
例如，jade-edit 提供官方知识编辑器参照，社区可以开发其他知识编辑器。
免费和收费应用均可参与，商业方向以推荐的 OpenBusiness 原则为核心。

用户按自己的选择组织“app 列表”并分享给其他人，
通过真实使用与个人推荐促进发现，使每类应用逐步形成几个不同特色的代表。
应用列表的结构、版本表达、分享和安装语义待设计；本文不把用户选择直接当成付费授权清单。

**官方应用的角色**：基础参考、生态能力示范与第一批用户的服务工具。
长期应用生态依赖市场与社区共建，官方和社区应用的宣传应公平。
建议将宣传/发现规则公开、官方与社区使用同一规则，并使推荐理由可解释；
这些具体治理机制是设计建议，尚需确认与验证。

应用市场的正式交付版本待定，不自动列为 v0.6 平台上线门禁。
v0.6 的应用独立化为市场准备工程基础；应用身份、版本、兼容性、发布描述和用户列表
可先做接口/原型研究，复用工具链与 AutoScape 的应用契约，避免各做一套不兼容机制。
成本分摊、价格形成、收益分配与社区治理应另行调研，按实验结果确定产品方案。

### 1.6 系统级 Package / Install（2026-10-03 用户确认）

这是 v0.6 必做方向。auto-man 从源码工程管理扩展到 AutoOS 各类实体，
统一身份、依赖网络、获取、制品存储与生命周期；知识包管理也是本版本工作，
不因完整知识管理流程在 v0.7 才成为主线而延期。

目标入口：`auto search "xxx"`、`auto install "xxx"`、`auto update "xxx"`、
`auto uninstall "xxx"`；Launcher 搜索后可安装，并共享更新/卸载与任务状态。
CLI 与桌面使用同一核心，应用市场不是基本安装能力成立的前置。

目标架构与验收建议见 [统一 Package / Install 设计草案](design/strategy/unified-package-install-strategy.md)。
应区分不可变发布包/制品与可变用户数据，统一核心由实体 adapter 提供各自生命周期。
Auto 原生依赖采用内容复用与映射，避免每工程复制整个依赖树；
遵守 worktree 禁止 junction/symlink 的约束，不照搬 pnpm 的链接布局。

建议先做真实单机安装闭环与代表性实体，再扩大宿主生态兼容。
安装事务、可恢复更新、用户数据归属与卸载语义须在设计阶段明确。
外部安装格式全面接管、复杂 registry/跨设备数据管理、完整应用市场等为 v0.7+ 候选。
新增主线会扩大关键路径，完整基线恢复后需重估年底范围，不沿用此前未含此项的工作量判断。

### 1.7 系统通信、AutoAI与系统级DevTools（2026-10-04 用户追加）

两项是实现AI版个人OS的公共基础：业务Service/Capability供应用与Agent共同调用；
DevTools在同一通信层提供系统级观察、操作与诊断，由OS组件提供人用界面和AI接口。
已有AutoUI活体VTree/MCP能力是可复用输入，不能把接口统一当作不同backend能力已一致。

推荐分层为：Auto task/msg的actor执行模型 → typed call/事件/流与长时任务 → Schema约束Atom数据 →
协商编码（Batom/兼容投影） → 本地IPC/外部bridge。DDS/ROS2、COM式接口思想、RPC与Atom编码
各处于不同层，具体组合与实现仍需RFC/能力探针；不直接冻结为某一个中间件或改写当前VM调度。

AutoAI暂作工作名，重点是可发现的业务能力、typed输入输出、effect、取消/收据、稳定对象引用、
增量/投影与可验证结果，降低完整任务的Agent轮数和token。原生应用内部可替代逐次MCP/CLI胶水，
对外保留MCP等适配；不能仅因二进制包变小就宣称LLM成本或可靠性提升。

建议v0.6最小范围：本机会话发现/调用与任务、Launcher→Notes真实捕获、统一Inspector与Agent接口、
VM和a2r/Rust的共同观察/动作子集、同场景的树/布局/截图比较、一个Qt或accessibility样板。
完整分布式发现、全部第三方应用覆盖、全面source debugger、时间旅行及全部应用迁移留v0.7+。
两项新增范围必须与其他主线重新排容量，不预先推迟原已确认目标，也不要求28app全部重写。

详细RFC归AutoOS仓：[应用通信/AutoAI](https://github.com/auto-stack/auto-os/blob/v0.6-dev/docs/design/strategy/auto-app-communication-v0.6.md)、
[系统DevTools](https://github.com/auto-stack/auto-os/blob/v0.6-dev/docs/design/strategy/system-devtools-v0.6.md)、
[共同分期与应用依赖](https://github.com/auto-stack/auto-os/blob/v0.6-dev/docs/design/strategy/v0.6-foundations-roadmap.md)。
它们为Draft技术建议，主力机恢复后按各仓正式取号并拆成中等Plan；近期可以先做独立schema、fixture与两进程原型。

## 3. 编译器主线：Atom/BAtom、HIR 与三个执行分支

### 3.1 目标架构（已确认）

```text
Auto Source → AST → 名称解析 / 类型检查 / 语义分析 → AutoHIR
                                                    │
                    ┌───────────────────────────────┼────────────────────────┐
                    ▼                               ▼                        ▼
              Native 后端                      A2X 后端                 VM CodeGen
                    │                               │                        │
             目标文件 / 链接                   Rust / C / Python             ABC
                    │                               │                        │
             原生可执行文件                    宿主工具链                    AVM
```

HIR 是核心工程，AC/AAC 是首个正式落地后端。HIR 稳定后，a2r、a2c、a2py 等
逐个改为独立 HIR 后端；在 12 月底目标下，全量正式迁移建议作为 v0.7 候选，
v0.6 保留代表性接入探针与设计验证。AVM 编译路径最终也迁移为
`AST → HIR → VM CodeGen → ABC → AVM`。AVM 执行的仍是 ABC。

### 3.2 Atom/BAtom 与 HIR 的边界

- 新版需求与格式候选见 [Atom/Batom v2 设计草案](design/strategy/atom-batom-v2-design.md)：
  独立模型与内存、Schema/struct 映射、Node/Lisp 数据文本、自描述 D 与 Schema 紧凑 S。
  本稿尚未冻结编码或实施计划，不替换当前 Value/Atom/旧 Batom。
- AutoHIR = Atom 核心结构模型 + HIR Schema + 编译器语义约束。
- Atom 文本视图和 BAtom 二进制表示服务检查、交换、缓存与工具消费。
- 内存表示可以是与 Schema 对应的紧凑类型结构，不要求每个 pass 操作动态属性表。
- 现有语言 Atom 与 Shell Atom/BAtom 的关系需先审查；不能直接假设 Shell BAtom
  就是通用、无损的 HIR 编码。附件/聊天中的实现判断须以代码核验。
- 需要定义无损往返、引用与 ID 完整性、版本识别、确定性、校验和不支持值的错误行为。
- HIR 保留高层结构和已解析语义，各后端执行专属 lowering；不强求一个低层 IR
  同时适合源码转译、VM 指令与原生机器码。
- AutoUI/AutoDown 等方言进入 HIR 的扩展边界，与拆仓插件契约共同设计。

### 3.3 Rust AC → Auto AAC → 自举闭环

1. 先以 Rust 实现 AC，复用可复用的现有前端能力，经 HIR 连接 native 生成器。
2. 以 Auto 实现编译器主体，按模块与 Rust 参照实现对拍。
3. Rust AC 编译 AAC 源码，生成第一代原生 AAC。
4. 第一代 AAC 编译自身，生成下一代；再重复一轮，验证结果与行为一致性。

自举范围必须包括所声明的编译器主体，不能只迁移 CLI 或包装 Rust 前端就宣称完成。
v0.6 的 Rust AC 与 Auto AAC/ACC 均沿 Cranelift 主路径：AC 直接调用，
AAC 经明确后端桥接调用，保留库/运行时/接口来源和版本清单。
薄 Rust C ABI 库为优先评估方案，独立后端进程也可作初期方案；具体接口按专项计划验证。
自举与自主机器码后端是独立演进轴，底层依赖全部改写成 Auto 不构成本版自举门槛。
a2r 可以辅助构建/验证迁移模块，但不能代替原生 AC/AAC 自编译闭环。

### 3.3.1 Pass、SSA 与自主后端分期（用户确认）

v0.6：Typed/Checked HIR → Auto 语义降级与基础优化 → Cranelift IR/SSA → native。
先明确效果/所有权/求值顺序、pass 前后条件、校验、诊断、来源和优化前后对拍；
不要求先自写整套 SSA 构造、通用优化器或机器码后端。

v0.7：Typed HIR → 自主低层 CFG/SSA → 自主分析/优化 → Cranelift 适配或自主代码生成。
具体 phi/block arguments、内存/effect 模型和进阶优化由实证设计决定。
按 target/profile/构建模式逐步并存，只有能力/ABI/正确性/收益/维护门槛达成才切主后端。
Cranelift 可保留参考/备用；公开 HIR 不强制变成 SSA，公开 ABI 不因后端变化自动改变。

完整比较和接口见 [AC/ACC 后端演进](design/strategy/auto-native-backend-evolution.md)。
Plan 741 继续只做首个有界 HIR/native 闭环；pass 框架、自举和自主后端分别制定后续计划。

### 3.4 HIR 稳定与迁移验收

- Schema、语义不变量、来源位置和版本演进规则明确。
- Atom/BAtom 的约定范围无损往返，非法结构和悬空引用能诊断。
- Rust AC 覆盖 AAC 自举所需语言能力、运行时、互操作与链接路径。
- 设计期即用 A2X 与 VM 代表性语料做探针，检验高层信息是否保留。
- 对拍结果覆盖输出、错误和相关行为，不仅比较一次成功编译。
- 自举一致性需控制非确定性因素，明确比较方式与差异处理。
- 正式迁移按后端/模块逐个替换；旧路径仅作为有退役条件的过渡参照。

### 5.1 挑选原则

用户最新补充：主机器已做到计划 739/740，而本地可见到 726。
近期优先“新方向的独立工作”，不续做既有计划、修复、优化或框架接线；
旧前端→新 HIR 的 adapter 也等完整基线恢复后再做。
第一批聚焦新 Atom/BAtom 模型、HIR/native 实验和独立安装事务核心。
另按用户补充增加 Demo 独立产品线：保留教学源，以新仓孵化产品；新增 submodule、
已有 OS app 目录迁移与启动来源切换分别验证，四大主力 app 暂不改动。

工作是否可提前做，应看合并时能否清楚迁移、是否依赖不可见工作，不能只看文件是否新建。
不同文件也可能修改同一语义或接口；当前快照“未引用”不等于最新代码无人消费。

| 工作 | 当前建议 | 回到完整基线后的处理 |
|---|---|---|
| Roadmap、架构边界、候选 Schema、验收设计 | 优先；现状判断标注快照，决策与事实分开 | 对照完整代码/新设计修订 |
| 拆仓依赖调查、迁移清单草案 | 可做只读调查，复用已有 Design 32/Plan 691 | 重扫最新消费方后才能据此删/搬 |
| 语言行为语料、自举需求清单、对拍设计 | 只作新实验的配套输入；现有自举/生态语料补齐不作为近期主线 | 核对 v0.5 新语义，接入正式验证 |
| Atom/BAtom 往返原型、HIR 校验/表示实验、native 后端选型探针 | 可作为隔离原型；不替换当前核心，不依赖猜测的新接口；正式实施仍走设计/Plan 流程 | 重新评审接口与数据模型，再迁入生产路径 |
| Linux/鸿蒙环境与生态 API 的独立探针、知识模型/示例工作流 | 可按依赖逐项确认；不预设最新 AutoUI/Musk 接口 | 用实际版本适配，重新执行必要验证 |
| 搬 crates、重命名公共 API、删除现有路径、改 parser/VM/生成器核心 | 暂缓这些直接重构 | 基于完整 v0.5 在专用计划 worktree 执行 |
| Demo 独立仓与 submodule | 可先做新增产品仓、来源快照、依赖适配和分批集成；保留教学源，四大 app 接入不动 | 对照完整 v0.5 源差异；已维护 OS 目录转 gitlink 逐 app 保全隐藏更新，验证实际启动源 |

建议近期按“roadmap 边界 → 架构 RFC → 语料/验收 → 一个隔离原型”的顺序推进。
可以产出代码原型，不把所有工作都限制为文档；原型是否保留取决于基线恢复后的评审。
不会影响 v0.5 的判断应有具体依赖证据，不能承诺未来零冲突。
