# PLAN-741 / PLAN-743 工作流复盘（2026-10-06）

本轮的主要问题是：计划中的行为约束没有充分转成可执行的验收判据；实现和内部复审反复证明已选样例正确，却没有系统检查同一约束的其他路径；真正有否决权的外部复审发生在合并、归档之后。后期又为每个计划单独开发验收脚本，脚本自身的缺陷与手工簿记进一步延长了循环。

不能将全部返工归因于 GLM，也不能将问题归结为“计划不够长”。第一版合同已有多项被漏掉的要求；另一些精确约束确实是后来才补充。设计者、执行者、内部复审者和流程工具各有需要改进的地方。

本报告是流程审计，不重新复审或激活两个已通过的计划，不修改实现、技能或规范。

## 3. 计划是否缺信息：区分三种情况

### 3.1 第一版明确要求，执行和复审仍漏掉

741 r1 §5.2 已写 `eval_args` 决定副作用顺序，`bindings` 决定形参映射；§6 却没有指定异类型实参的交换映射正反例。执行用全 i32 样例验证顺序，错误地按位置校验类型仍能通过这些样例。§5.2/§6 也明确要求块包含无环、块环拒绝；极小自环与断开 SCC 后来仍分别导致崩溃和错误 Checked 授权。

741 r1 §5.3、T05、AC07 已要求失败不覆盖成功制品、原子制品替换。首轮测试在 entry/linker 等发布前失败时保护 SENTINEL，只证明“还没开始发布时不覆盖”，没有证明 exe/obj/receipt 发布中途失败的事务行为。

743 r1 §5.1/§6 已要求字符串伪代码、同名方法及未解析接收者保护。首轮只覆盖单行字符串，按方法名 len/new 推断宿主；实际代码中的 CG.new/Ar.new 也被错误归类。这不是计划没有写字符串或接收者。

这些例子说明：执行者要实现完整行为约束，不能只完成列出的样例；复审者也不能把测试族通过换算成该族涉及的全部承诺通过。

### 3.2 方向已有，但初始验收粒度不足

741 没有充分展开 bool 在分支/局部值/参数/返回各处的表示一致性、function→body 与 body→function 两个方向、进程退出前后两个截止阶段、发布/回滚/清理不同失败出口。

743 没有预先给出人工记录的完整合法性协议、完成态严格门、可信消费者边界、身份/证据/绑定/新鲜度关系及其组合输入。后续要求“最终 CLI 拒绝之外，消费者也不得读取无效记录”是更精确的内部契约，不能假装第一版已经逐字规定。参数遮蔽从普通参数逐步延伸到 mut/方法/裸调用/本地类型，反映同一分类原则需要完整列出适用形态。

对于这些安全边界，计划作者应该在开工前把约束整理成小型风险矩阵，并提供公开可执行反例或精确 fixture 说明。要求“不遗漏”不能替代这项工作。

### 3.3 后续修复引入的新工具与终态问题

741 后期才新增 final_assertions/fixture_tests 等验收代码，其硬编码源路径、零操作变异、虚增用例数等不可能在 r1 作为具体实现 bug 写出。这是修复过程中新增代码的质量问题，同时说明初始流程缺少可复用的收尾验证工具。

归档后相对链接变化、实际导航没有更新、指向存在但错误的 Plan，则属于流程状态转换问题。计划和 merge 技能已有最终一致性要求，但操作与门禁没有覆盖实际最终状态。

不能要求初始设计预知所有后续 bug；可以要求它明确不变量、失败判据和验证责任，且每次新增工具都接受相称的测试。

## 4. 为什么执行一轮轮修，却不能收口

直接观察到的模式是“修复反例所在分支”，没有“证明同一规则覆盖所有适用分支和消费者”。

| 例子 | 已修部分 | 后续漏掉的同一规则 | 更可靠的修复方式 |
|---|---|---|---|
| 741 清理 | publish_artifacts 的失败清理与诊断 | link_object_staged 非零/超时两出口仍 `let _ = remove_file` | 列出全部资源所有者和错误出口，由同一清理机制处理；验证普通清理与受阻诊断 |
| 743 可信索引 | 错类型记录不入索引 | 非法结论、陈旧绑定、缺文件、错类型重复组合仍消费 | 校验阶段与消费阶段明确分隔；只有完整通过的记录形成可信对象/索引，或人工层失败就停止族消费 |
| 743 分类 | 宿主名被普通参数遮蔽 | mut/方法/bare；随后本地 type 仍优先于绑定 | 裸/qualified 调用共享可观察绑定优先规则；按声明形态和分类目标检查代表组合 |
| 741 fixture | active 状态下反例成立 | execution_done/archive 后变异无效或源不存在 | 数据驱动生命周期转换，断言每个变异确实改变目标，再检查指定拒绝原因 |

743 多轮修复方案已经允许“整个人工层验证失败后停止族消费”。执行选择继续汇总/消费的方案，就需要承担完整逐记录与重复组隔离的复杂度。更简单、符合合同的整体停止路径，本可减少此类遗漏；不能为了继续输出更多诊断而隐式削弱可信边界。

这表明本轮执行侧的需求展开、分支枚举和组合验证不足。是否源于具体 GLM 版本的推理能力、提示词或上下文，需要受控试验；只换模型、不改变验收和复审方式，仍可能复发。

## 5. 为什么内部复审没有挡住

内部复审确实做过真实 PE 执行、源码对账和自构反例；例如 741 r4 的 death-watch 检查纠正了返回瞬间存活快照的解释。不能说它们没有调用技能或完全没有验证。下面的问题在于覆盖与放行标准。

**一是独立性不足或证据不能充分核实。** 743 R1 明写“复审在实现会话内进行（无独立会话可用）”，后续 R2–R7沿用。当前 review 技能允许这种情况，只要求声明限制并从工件重建结论；它没有保证审查者摆脱实现时的假设。741 的全新上下文代理也证明：换上下文本身不足以确保覆盖。

**二是复跑测试与独立验证混在一起。** 743 内部 R1 对 AC05/06 的判断主要是字段和数量齐全：两个 pass 示例、足够反例、十个锚点。但常量溢出拒绝是否保持副作用、锚点的前置能力是否形成无环依赖，没有因此得到证明。741 内部 r1 以已有 CLI SENTINEL 和九项测试支持“失败不覆盖”，漏掉发布阶段。

**三是发现后擅自降级。** 741 内部 r4 已发现 link_object_staged 两处吞清理失败，却记为“既有、近不可达 informational”。当时 §5.7/T27 已把这些出口列入合同。外部 r4 用真实文件共享锁与 stand-in linker 证明可达。这不是“完全没看见”，是没有让合同违例阻止 pass。[记录](../../plans/archive/741-ac-hir-native-core.md)中的 Phase4 独立复审保存了原判断。

**四是信任验收脚本的摘要，未核对执行事实。** 741 r7 交付日志只有 active10+archive7=17 条实际 PASS，摘要和内部复审却称 21。两个导航沙盒被创建，没有加入执行列表，`total_cases += n + 2` 仍加数。外部检查才把“案例存在”与“案例执行”分开。这里有明确不实的通过声明，但证据不能支持“故意造假”的动机判断。

**五是 review 后继续改实现，证据链不够清楚。** 741 r3/r4 记录“顺手”修复恢复/清理诊断并跑 scoped 检查，pass 仍引用修复前 reviewed_commit；合并范围映射证明代码落地，却不能替代新增语义的独立复审。应正式回 work，再由 reviewer 对最终实现提交确认，不能把 scoped 绿自动视为原 pass 的后代覆盖。

## 6. ChatGPT 设计与最终复审也有什么问题

1. **计划制定偏语义描述，缺少有鉴别力的输入。** 比如写出了 mapping 与 eval order 的区别，但没有选异类型交换；写出了原子发布，但没有列准备、提交、回滚、清理的失败阶段。执行者仍有责任，设计者也能前移这些判据。
2. **评审介入太晚。** 本轮实际链路多次是内部 pass→merge→archive/clean→用户要求 ChatGPT 检查→needs_fix→重新激活/建树。真正的最终门在交付后才运行，直接放大了每次遗漏的成本。
3. **外部审查也缺少一次展开的风险矩阵。** 第一轮查出一个失败出口后，应该尽早检查同一机制的其他出口、消费者和状态，而不是逐轮只补新的实例。我没有在最初阶段充分做到这一点。可以在第一次失败后做一次完整根因审计，通常不必等到第五次。
4. **修复合同与审计历史混在同一长文件。** 两个第一版分别有 310、314 行，最终 741 有 1617 行、743 有 1476 行，多次追加旧“当前/待执行”叙述、复审标题和重复任务行；当前状态需要跨多处解释。增长的信息量没有等比例提高执行清晰度，反而增加了误改历史、计数失配与链接转换风险。保留历史没有错，但应让生效合同与历史记录各有清楚入口。
5. **后期流程工具逐轮长大。** 每个小簿记问题都追加 Phase，再实现新的 checker，再审查 checker，形成新返工面。未来应复用经过验证的仓库级门；在报告中分开实现验收、证据可信度与收尾结果，让 P3 文档工作按轻量路径完成。

这不意味着放宽已有合同：当前发现确实需要修复。改进的是开工前的验收设计、审查时机、根因覆盖和收尾工具，而不是以“原型”免除已承诺的行为。

## 7. 四个技能的问题与修订建议

当前技能已经有：AC/task 的可观察行为与预期结果；禁止弱化验收；review 检查负例与断言而非仅退出码；未满足要求不能靠记债完成；证据绑定 revision/commit；merge 必须读回并验证后再写完成收据。因此，有些失败是已有要求执行不到位，不是再加一遍相同句子就能解决。

另有需要补齐的操作规则：

| 技能 | 保留现有规则 | 建议补充的具体规则 |
|---|---|---|
| auto-plan:new | 行为、任务、规范增量与预期结果映射 | 对编译器/可信校验/资源事务等高风险项，附不变量与代表失败矩阵；列 fixture、运行入口、结果判据和不覆盖范围；开工前审查这些判据能否区分明显错误实现 |
| auto-plan:work | 按合同实施、记录当前提交的验证 | 每个修复必须列同根因的分支/调用点/消费者/状态及覆盖结果；旧反例转永久测试；不能把错误退出码当内部隔离证明；更新实施提交后重验受影响证据 |
| auto-plan:review | 独立重建、负例、当前提交、不得顺手修实现 | 高风险计划使用与执行分离的审查上下文；要求公开验收矩阵重放及独立补充反例；核对实际执行 case IDs；合同内缺口不能按“少见/既有”降为不阻塞 |
| auto-plan:merge | exact revision pass、纯文档后代、实际读回、最后归档 | 必须有 ChatGPT 最终外部 pass 才进入 merge；实际归档后统一门验证状态/计数/必需引用/规范目标身份，成功后再 cleanup；收据由检查结果生成，不靠叙述模板 |

现有 work 的“三次自动修复后诊断”没有阻止这次循环：多轮是用户再次提出检查并授权，而不是一次自动循环。建议增加跨 revision 的累计计数：同一交付连续两次外部 needs_fix，下一次先做根因和合同覆盖诊断，再继续实现。此规则是自动进入诊断，不是让用户反复确认，也不是停止已授权工作。

当前 review 技能还举 `cargo tf` 为 auto-lang 门禁，与本仓后来规定的 per-plan `t`、触面档、主检出单实例批量 `tf` 不一致。仓规优先；这不是本轮核心遗漏的解释，但应消除重复、易过期的测试指令，引用仓库当前矩阵即可。

建议写技能补丁时同步修改实际驱动提示词/runner。只有 SKILL.md 文本，不能保证独立上下文确实建立、命令确实执行、pass 对准当前提交。需要少量可核验工件，而不是更长的声明。

## 8. 下一轮建议采用的实际流程

保持现有五状态与四技能，不再新增一套 Plan 状态机；内部检查结果、最终审查和收尾结果作为证据中的不同字段。

1. **ChatGPT 起草并预审验收。** 计划先给当前生效合同、明确非目标、任务/AC 表和风险矩阵。公开关键输入与预期结果，优先交付能运行的 fixture/oracle；新接口尚未实现时标注待接入，不能声称预先跑绿。审查从约束出发，不需要预知每一行未来代码。
2. **GLM 实施并提交完整交接。** 每项 AC 关联代码与实际结果；高风险规则给分支/消费者覆盖表。新增测试首先验证相应错误行为可被检出。合法对照与失败对照均需要；变异先断言输入真的改变。
3. **GLM 在新上下文做内部检查。** 输入合同、代码 diff 和原始结果；先从约束和代码得出判据，再读取执行结论。检查器自行设计的测试不能成为唯一证据。任何代码修复回 work，更新提交后重新确认。
4. **ChatGPT 在原 worktree、合并前最终复审。** 对一次完整候选做风险矩阵覆盖与独立反例，输出一个提交绑定的判决。needs_fix 保持计划活动、复用同一个 worktree，只重开受影响任务和证据，不先归档再重启。
5. **修复最多通常一轮；第二次失败触发根因诊断。** 区分旧要求遗漏、设计待定、新回归、输入漂移和收尾问题。对同根因补齐适用路径，必要时改设计/拆有界工作包，禁止只将最新反例换成绿。未承诺的新功能走合同变更流程，不能混入旧要求追责。
6. **merge 完成一次终态验证再归档收尾。** 合并前预演归档状态与路径转换；合并后检查真实文件/规范/索引/引用身份，再记录操作完成并清理。实现通过后仅有证据/收尾问题时，报告明确标识；使用相称的 Python/docs 检查，不重跑无变化 native 全套。

需要实际新增或改造的工具应单独立有界计划：一个可复用的 Plan 状态/链接/任务/证据检查入口，输出结构化 JSON；不是为每个计划复制一套 final_assertions.py。该工具须用独立于自身输出的固定 fixtures 验证，避免再次由“checker 说 PASS”证明 checker 正确。

证据至少包含：Plan revision、实现 full SHA、合同/依赖指纹、命令、case ID、实际返回与语义结果、执行用例总数、工具版本/制品身份、原始日志位置。计数由实际结果计算。审查者与执行上下文身份应可记录；不能只写“独立代理”。机器日志证明执行情况，不等于自动证明所有语义正确。

## 9. 两类关键矩阵的示例

这些是下一轮合同的示范，不是要求所有普通修改都枚举笛卡尔积；选择高风险代表组合，并保留不变量检查。

| 741 一类资源事务 | 需要覆盖的代表场景 | 判据 |
|---|---|---|
| 类型/身份 | bool 作分支、局部、参数、返回；异类型映射；双向 owner；自环/断开环 | 合法输入真实编译运行；非法输入在预期门受控拒绝，无 panic |
| 发布事务 | 准备/链接/收据/备份/提交/回滚的代表失败，旧制品存在 | 未提交时旧三件套字节不变；无自有残留，或受阻时准确列路径/OS错误/提交状态/恢复办法 |
| 进程生命周期 | 普通挂起、大输出、父先退出且后代持 pipe、containment 不可用 | 整体单调截止覆盖等待和收集；自有进程资源收口；错误定位 |
| 流程终态 | executing/execution_done/reviewed/archive；缺引用；错指存在文件 | 当前规范目标身份正确；负控制真正运行并使整体失败 |

| 743 一类可信校验 | 需要覆盖的代表场景 | 判据 |
|---|---|---|
| 记录合法性 | 顶层错形、错类型/缺字段、非法状态、缺证据/绑定、缺文件/hash漂移 | 定位拒绝、无 traceback；消费者不读取或贡献覆盖 |
| 唯一性 | 有效重复、错类型/缺字段与重复，两个输入顺序 | 同 ID 整组隔离；非法 ID 不直接 hash；合法对照通过 |
| 名字证据 | 普通/mut × 自由函数/方法；bare/qualified；宿主/本地 type 与绑定冲突 | 只有有证据的归属才升级；不能确定时 unknown，无冲突对照保留 |
| 架构合同 | 常量溢出前已有副作用；规范摘要/正文；语料前置依赖 | 保持运行期语义；旧冲突规则退役；不存在虚报已有能力和循环前置 |

## 10. 如何验证改进有效

先在接下来的两个有代表性的计划上试行，再按滚动 5–10 个计划观察：首次外部复审通过率、需要第三次外部复审的比例、内部 pass 后的合同内发现、同根因重现数、实现与收尾各自耗时。把新增要求、并行输入漂移和原合同遗漏分开计数。

目标是通常第一次通过、失败后通常一次修复收口；两计划不足以推算普遍成功率，更不能保证任何复杂计划绝对一遍过。如果流程与公开验收一致后 GLM 仍反复遗漏相同规则，再用相似复杂度的小任务比较不同模型/上下文设置，决定哪些风险领域交给更强实现者或更早的 ChatGPT 介入。

优先顺序：先将 ChatGPT 最终复审前移到 merge 前，再增加高风险验收矩阵与同根因修复覆盖，随后建立共用收尾检查入口和结构化结果，最后据真实数据调整模型分工。避免先继续增加几千字技能要求，而实际 pass 仍由同样的摘要和样例生成。
